Can Jev flag risky code changes before CI runs?

Jev is TypeSafe's fast decision model: it answers typed questions (yes/no, choice or score) with a probability. Here it answers four yes/no questions about each change. Loading the results…

Passed our tests · not in use yet Next: a trial in analyze-stock-kpi, where Jev comments on each pull request but never blocks it, compared with what human review finds.

What it checks

Jev answers four yes/no questions about each change, seeing only the commit message and the diff. The score is how well it tells flawed changes from clean ones: ROC-AUC, the chance that a random flawed change scores higher than a random clean one (1.0 = perfect, 0.5 = guessing). Open a row for the exact question.

    Why Jev, and what else is there?

    For this job, measured here

    • Pro: tells flawed from clean changes nearly as well as Claude Sonnet and Opus and better than Haiku (0.94 against 0.96, 0.97 and 0.90 on average), in about a third of a second and for about a hundredth of a cent. Cheap and fast enough to check every change.
    • Pro: no GPU or model hosting; one HTTPS call, from Python or BAML with the same results.
    • Con: the diff leaves your machine for a hosted, paid service, so it doesn't fit code that must stay private.
    • Con: on 2026-09-23 TypeSafe's firewall blocked 4 of the then 60 changes (none since); a check must treat "blocked" as its own outcome.

    Others building on Jev (their claims, not measured here)

    • abide (MIT) makes Claude Code, Codex and OpenCode follow a repo's AGENTS.md rules: it asks Jev one question per rule on every edit and has the agent repair a break. The same idea as this test, packaged for everyday use.
    • jev-ultrafast (MIT, Browser Use) is a web agent whose every step is a Jev decision.

    An open alternative (not measured here yet)

    • Laya (Apache-2.0) is an open-weight decision model with the same typed questions, run locally or self-hosted behind a Jev-compatible API. It could remove both cons above (data stays local, no per-call bill), but its accuracy on this task is unknown. Its own README says its Jev comparison was never measured against the live Jev API. Next step here: run it on the same 184 changes.

    How we tested it
    Examples
    184 real commits from four public repos: analyze-stock-kpi, polyfetch-scrape, doc-pipeline-engine and Agents-eval.
    Labels
    59 clean and 125 flawed (30–37 per kind of flaw). Most flawed examples are a real commit with one flaw added; two are real commits that already had one.
    Asked
    Five times per change; the answers agree 97–100% of the time. Jev is called with and without BAML.
    Speed and cost
    Per request as logged. End to end, including start-up, one check took p95 3.15 s without BAML and 2.94 s with it (10 runs each, 2026-09-23). Cost counts input tokens × $0.042 per million (typesafe.ai); no output price is published. Claude's cost is what its CLI reports at list price.
    Firewall
    TypeSafe's firewall blocked 4 changes on 2026-09-23 and none since. Setups are always scored on the changes all of them answered.
    Why ROC-AUC
    It doesn't depend on a threshold. Jev returns probabilities while Claude states a number when asked, so ranking quality compares them fairly. What happens at the actual setting is covered by "flags" and "wrongly flags" and the strictness slider. It doesn't show calibration or rare-class precision; those metrics are planned.
    Lesson
    Ask about what is in the input. "Is this abstraction used only once?" needs the whole codebase, which Jev never sees; "…that nothing else in the diff uses?" took wrongly flagged clean changes from 6.7% to 0% on the same 60-change set.
    Caveats
    Flaws are mostly added on purpose. "Clean" labels come from rules plus one audit, not a manual review.
